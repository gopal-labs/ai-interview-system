# Question Topic Classifier

## Overview

This project is a machine learning system that classifies technical questions into one of four topics: OOP, Database, Networking, or Machine Learning. It is built with Python, scikit-learn, and NLTK. Questions are pre-processed with stop-word removal and lemmatisation, converted into TF-IDF vectors, and then classified using Logistic Regression.

The system also handles multi-topic questions by reporting a secondary topic when the top two predictions are close in confidence, and flags low-confidence results so the caller can decide how to handle them.

## Folder Structure

    question-classifier/
    |
    |-- classifier.py       Core QuestionClassifier class (pre-processing, training, prediction, persistence)
    |-- dataset.py          Labelled training data (40 question-topic pairs, 10 per class)
    |-- train.py            Script to train the model and save it to disk
    |-- evaluation.py       Script to measure held-out accuracy on a random 80/20 split
    |-- test.py             Interactive command-line interface to query the trained model
    |-- model.pkl           Saved Logistic Regression model (auto-generated by train.py)
    |-- vectorizer.pkl      Saved TF-IDF vectoriser (auto-generated by train.py)
    |-- README.md           Project documentation

Note: model.pkl and vectorizer.pkl do not exist until you run train.py. They are generated automatically and should not be committed to version control.

## How to Run

All commands should be run from inside the project folder.

    cd question-classifier


Step 1: Train the model

    python train.py

This trains the classifier on the full dataset and saves two files to disk: model.pkl and vectorizer.pkl. It also prints a training-set accuracy report so you can confirm the model fit correctly. You must complete this step before running test.py.

Expected output:

    Accuracy: 100.00%
    ...
    Model saved successfully.


Step 2: Check held-out accuracy (optional)

    python evaluation.py

This performs a stratified 80/20 split, trains on the 80 percent portion, and evaluates on the remaining 20 percent. It prints accuracy along with per-question detail so you can see exactly which questions were misclassified. This step does not overwrite the saved model.

Expected output:

    Hold-out test accuracy: 75.00%
    Test set size: 8 samples

      [CORRECT]  actual=OOP                   predicted=OOP            question=What is abstraction?
      [CORRECT]  actual=Database              predicted=Database        question=What is normalization?
      ...


Step 3: Run the interactive interface

    python test.py

Type any technical question and press Enter to classify it. Type "exit" to quit. If model.pkl does not exist yet, the program will tell you to run train.py first.

Example session:

    Question Topic Classifier
    Type a question and press Enter to classify it.
    Type 'exit' to quit.

    Enter Question (or 'exit'): What is a foreign key?

    Result:
      Topic      : Database
      Confidence : 72.14%

    Enter Question (or 'exit'): How does a neural network relate to overfitting?

    Result:
      Topic      : Machine Learning
      Confidence : 45.23%
      Also relates to: OOP

    Enter Question (or 'exit'): exit
    Goodbye.

## Output Format

The predict method in classifier.py returns a Python dictionary.

Standard result:

    {
        "topic": "Database",
        "confidence": 0.7214
    }

When the top two predictions are within 0.15 confidence of each other, a secondary topic is included to indicate the question spans multiple areas:

    {
        "topic": "Machine Learning",
        "confidence": 0.4523,
        "secondary_topic": "Database"
    }

When confidence falls below 0.30, or the input is empty or contains only punctuation, an uncertain flag is added:

    {
        "topic": "Unknown",
        "confidence": 0.0,
        "uncertain": True
    }

## Known Limitations

The model is trained on a small dataset of 40 questions, 10 per class. While it achieves 100 percent accuracy on the training set (it effectively memorises the examples it has seen), held-out accuracy on the 20 percent test split is lower because the vocabulary in unseen phrasings does not always overlap with training vocabulary. This is expected behaviour for a small dataset and not a flaw in the code. The most effective improvement is to add more varied training examples per class.

Out-of-scope questions, meaning anything outside the four topics such as "What is the weather?", are not refused outright. The classifier always assigns the most likely of the four topics. The uncertain flag is provided so callers can choose to handle these cases differently, but the flag is a heuristic and will not catch every out-of-scope question.

The secondary topic threshold and the confidence threshold are fixed constants chosen on the current dataset. They may need adjustment if the dataset grows significantly or new topic categories are added.

## Challenges Addressed in This Task

This section describes the challenges that existed in the original implementation and how each one was resolved.


### Return type mismatch causing accuracy to always read as zero

The predict method returned topic labels as numpy.str_, a NumPy internal string type, rather than plain Python str values. When evaluation.py passed these predictions to sklearn's accuracy_score alongside plain Python str labels from the dataset, the comparison failed silently and the function always returned 0.0 percent even when the predictions were textually identical to the labels. The same issue affected the secondary_topic field. Both fields are now cast to str before being placed in the result dictionary.


### Empty and punctuation-only inputs producing misleading predictions

Passing an empty string or a string made entirely of punctuation such as "!@#$%" to predict caused the TF-IDF vector to be all zeros, which made every class appear equally likely. The model would return a prediction with very low but non-zero confidence, giving the caller no indication that the input was meaningless. The predict method now checks whether anything meaningful survives pre-processing and returns topic "Unknown" with confidence 0.0 and the uncertain flag before the vectoriser is ever called.


### No signal for low-confidence or out-of-scope predictions

Questions that fall outside the known topics, or that are phrased in a way the model has not seen, were returned with exactly the same output structure as high-confidence predictions. There was no way for a caller to distinguish a confident classification from an uncertain guess. A confidence threshold constant was added. When the top prediction falls below it, the result includes "uncertain": True so downstream code can decide whether to accept, reject, or escalate the classification.


### Model files saved to the working directory instead of a fixed location

The original save and load methods opened model.pkl and vectorizer.pkl as bare filenames. These resolved to whatever directory the script happened to be run from. Running train.py from a parent folder would write the files to the wrong location, and a subsequent call to load from a different directory would raise an unformatted FileNotFoundError with no guidance on how to fix it. Both methods now resolve file paths relative to the directory that contains classifier.py itself using os.path.abspath and os.path.dirname on __file__, making the location consistent regardless of where the script is invoked. The load method also raises a descriptive error message pointing the user to run train.py if the files are missing.

### No error handling when the model file is missing at startup

If model.pkl did not exist because train.py had not been run yet, test.py raised a raw Python traceback with no explanation. The file now catches FileNotFoundError on load, prints a clear message instructing the user to run train.py first, and exits cleanly with a non-zero status code.


### numpy.str_ in the secondary topic field

The same return type issue that affected the primary topic field also affected secondary_topic. It was resolved in the same fix by casting to str before inserting into the result dictionary.

### Dataset Generation and Balance

The original implementation used a small manually written dataset with only a few examples per topic. This created several problems:

- Limited vocabulary coverage
- High variance in evaluation scores
- Overfitting to specific question patterns
- Poor generalization to unseen phrasings

For example, the model might learn the phrase:

    "What is TCP?"

but fail to recognize:

    "Explain TCP/IP model"

because the wording had never appeared during training.

To address this, a dataset generator was introduced.

The generator creates balanced training samples using topic-specific keywords and multiple question templates.

Each topic receives the same number of examples:

    OOP                100
    Database           100
    Networking         100
    Machine Learning   100

Total: 400 samples

The generator produces different styles of questions:

- Definition questions
- Conceptual questions
- Comparison questions
- Scenario-based questions
- Interview-style questions

Examples:

    What is inheritance?
    Explain inheritance.
    Why is inheritance important?
    What problems does inheritance solve?
    How would you implement inheritance in a project?

This increases vocabulary diversity and improves the model's ability to generalize to unseen questions.

The dataset generator also ensures class balance, preventing the model from becoming biased toward any particular topic.

## Design Decisions

TF-IDF with bigrams was chosen because short technical questions rely heavily on two-word phrases such as "primary key", "neural network", and "IP address". Bigrams allow the vectoriser to capture these phrases directly rather than treating each word independently.

Logistic Regression was chosen over more complex models because the dataset is small and the four classes are well separated by vocabulary. A more complex model such as a neural network would overfit even more severely at this scale and would add training time with no accuracy benefit.

The secondary-topic gap of 0.15 and the confidence threshold of 0.30 were chosen empirically on the current dataset. Both constants are defined at the top of the QuestionClassifier class and can be adjusted without touching any other part of the code.
